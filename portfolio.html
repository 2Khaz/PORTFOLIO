  1. 01수집 기준

    수집 기준과 표시 항목 정의

    상황
    여러 페이지에서 인기 게임을 건별로 확인하면 어느 나라에서 어떤 기준으로 순위가 매겨졌는지 놓치기 쉬웠습니다. 반복해서 비교할 수 있도록 지역과 지표를 고정할 필요가 있었습니다.
    행동

    한국 Steam 판매 상위 100개와 한국 Google Play 게임 매출 상위 100개를 각각 수집하도록 정했습니다. 판매 순위와 매출 순위는 지표가 달라 합산하지 않고 화면에서 구분했습니다.

    Steam은 순위 목록에 앱 식별자, 개발사, 장르, 가격·할인 상세를 붙였습니다. 상세 조회는 한 번에 몰아 요청하지 않고 다섯 개씩 묶었으며, 일시적 응답 실패에는 재시도를 뒀습니다.

    결과
    두 플랫폼의 순위와 게임 속성을 같은 화면에서 각각 읽을 수 있는 수집기와 출력 구조를 구현했습니다. 상위 100개는 조회 범위이며 항상 100개의 상세 정보를 확보했다는 측정 결과는 아닙니다.
    배울점
    데이터를 모으기 전에 지역·순위 기준·수집 범위를 고정해야 다음 기록과 비교할 수 있습니다. 순위에 가격이나 장르를 함께 두면 움직임의 맥락을 살피는 데도 도움이 됩니다.
    구현 데이터 항목

    같은 지역에서 서로 다른 순위 기준을 병렬로 수집

  2. 02이력 관리

    순위 변동과 과거 이력

    상황
    최신 순위로 계속 덮어쓰면 신규 진입, 상승과 하락, 연속 등장 여부를 비교할 수 없었습니다. 게임 이름이 바뀌어도 이력에서 같은 게임으로 찾아야 했습니다.
    행동

    이전 순위를 앱 식별자 기준으로 조회해 현재 순위와 비교하고, 이전 목록에 없던 항목을 구분했습니다. 최신 데이터와 수집 시점별 스냅샷을 따로 쓰고, 이력 파일 목록을 저장해 화면에서 선택할 수 있게 했습니다.

    이름 대신 앱 식별자로 연속 등장 기록을 관리해 동일한 게임을 구별했습니다. 화면에서 장르 분포, 순위 이동, 연속 진입 기록을 확인할 수 있도록 구성했습니다.

    결과
    최근 순위만 보여 주던 구조를 과거 시점을 선택할 수 있는 화면으로 확장했습니다. 연속 기록은 저장된 수집 회차 기준입니다.
    배울점
    변화를 보여 주려면 현재값뿐 아니라 비교할 이전값, 동일 대상을 연결하는 키, 기록을 고르는 방법이 함께 있어야 합니다.

  3. 03운영 복구

    시트 전송 실패의 분리와 재처리

    상황
    수집은 끝났는데 Google Sheets에 쓰지 못하는 경우가 생길 수 있었습니다. 실패를 수집 전체의 실패로만 다루면 이미 확보한 순위를 다시 수집해야 합니다.
    행동

    전송에서는 인증을 갱신해 재시도하고, 임시 탭에 먼저 기록한 뒤 기존 탭을 교체하는 절차를 뒀습니다. 전송을 끝내지 못하면 수집 데이터를 대기열에 남겼습니다.

    재전송을 별도 스크립트로 분리했습니다. 저장에 성공한 대기 항목과 재시도가 필요한 항목을 나눠 처리하도록 했고, JSON 이력 저장은 시트 전송과 구분했습니다.

    결과
    수집 결과를 재사용해 시트 쓰기만 다시 할 수 있는 경로를 구현했습니다. 저장소에서 재전송 스크립트 추가와 현재 대기열 처리 코드를 확인할 수 있습니다.
    배울점
    외부 서비스 연동은 실패 위치를 구분하고 단계별로 재실행할 수 있게 설계하는 편이 복구에 유리합니다.

  4. 04문서화

    대시보드와 구축 가이드 정리

    상황
    사이트 화면만 있으면 배치 작업이 어떻게 시작되고 수집·저장·시트·알림 중 어디에서 실패했는지 다른 사람이 파악하기 어려웠습니다.
    행동

    정기 호출에서 GitHub Actions, 수집기, JSON 이력, GitHub Pages, 시트와 Discord로 이어지는 구조를 문서화했습니다. 일반 실행과 복구, 테스트 실행을 따로 설명했습니다.

    수집 응답, 로컬 파일 생성, 시트 쓰기·읽기·교체, 알림을 각각 확인하는 테스트 절차를 준비했습니다. 사이트 구조 변경, 화면 미반영, 알림 실패처럼 대응이 다른 경우도 나눴습니다.

    결과

    배울점
    운영 문서에는 설치 순서뿐 아니라 정상 출력이 무엇인지와 실패했을 때 어느 단계부터 확인하는지도 있어야 합니다.

  1. 01콘셉트 기획

    세 공정을 하나의 의뢰로 설계

    상황
    타일 공사라는 소재로 서로 다른 조작을 넣으면서도 세 미니게임을 이어 붙인 것처럼 느껴지지 않도록 해야 했습니다. 팀장으로서 공통 콘셉트와 시스템 문서를 정리했습니다.
    행동

    철거는 타격으로 공간을 비우는 감각, 도포는 빈 곳을 메우는 감각, 시공은 조각을 맞춰 마무리하는 성취감을 목표로 뒀습니다. 같은 작업 공간을 손보면서 조작의 감각이 순서대로 바뀌도록 연결했습니다.

    로비 → 의뢰 선택 → 철거·도포·시공 → 정산 → 로비 흐름으로 구체화했습니다. 초기 의뢰 선택은 무작위로 제시되는 세 의뢰를 두고, 90초 안에 성패가 갈리는 짧은 반복을 유지하는 방향을 잡았습니다.

    결과
    본인 작성 콘셉트 기획서와 시스템 가이드에 세 공정의 의도, 의뢰 선택과 점수·보상, 로비 복귀를 연결한 흐름도를 남겼습니다.
    배울점
    여러 조작을 묶을 때는 입력의 종류보다 앞 단계가 다음 단계의 목표에 왜 필요한지 설명해야 하나의 작업 경험으로 읽힙니다.

  2. 02도포 규칙

    도포 진행률과 완료 판정

    상황
    도포에서 빈 곳을 채우는 감각을 살리려면 화면에 보이는 도포 상태와 실제 클리어 기준이 맞아야 했습니다. 같은 위치를 반복 입력해 진행량만 늘어나는 경우도 막아야 했습니다.
    행동

    바닥을 128×128 셀로 나누고 이미 칠해진 셀은 중복 집계하지 않는 방식으로 판정을 구체화했습니다. 99%를 충족하는 정수 기준으로 올림값 16,221셀을 사용했습니다.

    경계 검증에서 16,220셀의 미완료와 16,221번째 셀의 최초 완료를 구분했습니다. 초기 테스트가 이미 칠한 중앙 셀을 다시 찍는 바람에 완료되지 않자, 기준이나 기대값을 낮추지 않고 미도포 셀을 입력하도록 테스트를 고쳤습니다.

    결과
    도포 로직 커밋에 중복 입력과 완료 직전·직후의 동작이 기록됐습니다. 감각적인 요구를 개발 과정에서 검증할 수 있는 상태와 숫자로 연결한 결과입니다.
    배울점
    판정이 예상과 다를 때 규칙이 틀린 경우와 테스트가 기대한 상태를 만들지 못한 경우를 먼저 나눠야 합니다.
    구현 검증 데이터

    99% 도포 완료 판정의 경계값

    판정판 128 × 128 = 16,384셀. 완료에 필요한 셀 수는 16,384 × 0.99를 올림한 16,221셀입니다.

    테스트 조건도포 셀기대 동작
    기준 직전16,220완료 신호 없음
    미도포 셀 1개 추가16,221처음 한 번 완료 신호 발생
    완료 후 추가 입력16,221입력을 거부하고 셀 수 유지

    초기 테스트 입력이 이미 칠한 중앙 셀을 다시 찍어 경계값에 닿지 않았습니다. 판정 조건을 바꾸지 않고 미도포 셀을 찍도록 테스트 입력을 수정했습니다.

  3. 03시공 규칙

    난도별 조각 구성과 퍼즐 생성

    상황
    시공 난도를 조각 수로만 올리면 너무 얇거나 비슷한 조각, 겹치는 조각이 나와도 어려운 퍼즐로 처리될 수 있었습니다.
    행동

    쉬움 8개, 보통 10개, 어려움 12개로 나누되 생성 결과를 따로 검증하는 구조를 뒀습니다. 동일 시드로 문제를 재현하고, 볼록성·최소 두께·면적·겹침·모양 다양성을 검사했습니다.

    조각 수를 맞추는 검증과 플레이할 수 있는 기하 형태인지 검증을 구분했습니다. 모바일 실기 검증은 후속으로 두고 Windows 세로 9:16 대응은 별도 변경으로 다뤘습니다.

    결과
    조각 데이터와 시드 기반 생성기가 커밋으로 남았습니다. 해당 변경이 다루는 범위는 생성·검증 단계로, 이후 인게임 통합이나 모바일 테스트와 구분합니다.
    배울점
    절차적으로 만드는 콘텐츠는 개수와 난도 표기만으로 품질이 보장되지 않습니다. 문제를 재현할 식별자와 결과를 걸러낼 검사가 함께 있어야 합니다.

  4. 04평가·정산

    정산과 후속 성장 설계

    상황
    후속 논의에서 완료 시간·중복 도포·잘못 놓기 횟수로 S/A/B 등급을 주자는 안이 나왔습니다. 집계값을 그대로 쓰면 정상적인 플레이가 실수로 평가될 수 있었습니다.
    행동

    도포 중 브러시가 겹치는 것은 정상이고 아이템 때문에 여러 번 칠할 수도 있다고 지적했습니다. 타일을 잠시 내려놓은 행동과 실제 스냅 실패를 같은 실수로 셀 수 있는지도 검토했습니다.

    강제 등급은 빼고 총점과 골드 보상을 연결하며 통계는 평가와 분리했습니다. 범위를 넓히기보다 기존 세 공정과 7종 아이템을 유지하면서 보상 → 골드 → 상점 순환을 우선했습니다. 정산 진행·점수 원장·보상 계산·저장 책임을 분리하는 구조도 검토했습니다.

    결과
    후속 설계에 총점·보상·상점 우선순위가 남았습니다. 상점은 초기 4칸에서 3칸, 의뢰 종료 뒤 무료 재입고, 100골드 즉시 갱신, 재고·보유 상태 저장으로 구체화했습니다.
    배울점
    측정할 수 있다는 이유로 점수를 매기면 안 됩니다. 지표가 실제 플레이 의도와 실력을 구분하는지 먼저 따져야 평가를 납득할 수 있습니다.
    후속 설계 비교

    등급 제안에서 점수·골드와 별도 통계로

    제안문제수정 방향
    중복 도포 횟수 감점자연스러운 겹침·아이템 사용도 실수로 집계될 수 있음강제 등급에서 제외하고 통계와 평가 분리
    잘못 놓기 횟수 감점잠시 놓는 행동과 스냅 실패의 구분이 필요명시적 도전 조건과 기록으로 구분
    신규 콘텐츠로 반복감 해소추가 제작 범위가 커짐세 공정 유지, 점수 → 골드 → 상점 순환 우선

    출처: 후킹·차별화 개선제안 및 통합 로드맵 · 후속 설계 기록

  5. 05UI 후속 검수

    상점 UI 분리와 아이템 버튼 연출

    상황
    상점 화면을 나누고 망치 버튼이 활성화된 느낌을 주면서도, 버튼 바깥 형태가 흔들려 원래 UI로 보이지 않는 문제는 피해야 했습니다.
    행동

    버튼 실루엣과 외곽은 고정하고 내부 사선 무늬만 움직이도록 요청했습니다. 흐름 방향을 수정한 버전을 GIF·MP4로 비교했습니다.

    전달용 상점 이미지 12종의 파일을 확인했을 때 RGB로 저장돼 알파가 없었습니다. 화면의 시각안과 투명 PNG라는 실제 납품 규격을 별도 항목으로 확인했습니다.

    결과
    외곽 고정과 사선 방향 수정이 적용된 연출 작업본이 보고서에 남았습니다. Windows 제출본의 오프닝·로비·의뢰·세 공정·정산·저장 흐름도 보고됐지만 후속 UI 적용은 별도입니다.
    배울점
    UI 피드백은 움직이지 않아야 하는 부분과 바꿀 부분을 정확히 나누고, 넘길 때는 파일 형식·투명 여부까지 확인해야 개발에서 같은 결과를 얻을 수 있습니다.

  3. 03장르 전환

    장르 변경에 맞춰 전투·정비·저장 개정

    상황

    행동

    전투 → 정비 → 다음 웨이브로 진행을 다시 짜고, 20웨이브의 보스를 처치하면 종료하도록 정의했습니다. 정비에서는 레벨업 시 증강, 파츠를 획득했을 때 로봇 정비, 매 웨이브 종료 시 상점 순으로 진행합니다. 뒤 단계로 넘어가면 이전 단계로 돌아갈 수 없도록 했습니다.

    게임 진행·웨이브·플레이어·전투 관리 책임을 나눴습니다. HP·레벨·증강·파츠는 런 종료 시 초기화하고, 기체·콘텐츠·도감 해금은 영구 데이터로 보존하도록 바꿨습니다.

    결과
    개정 총괄기획서 22쪽에 전투와 정비의 순서, 단계 진입 조건, 저장 범위를 연결했습니다. 정비 시안에서 순서와 뒤로 갈 수 없는 조건을 시각화했습니다. 일부 개요에는 초기 탈출 문구가 남아 있었습니다.
    배울점
    장르가 바뀌면 전투만 개정할 수 없습니다. 무엇이 성공인지, 보상이 언제 반영되는지, 런을 끝낼 때 어떤 정보가 남는지까지 한 번에 검토해야 규칙이 서로 맞습니다.

  4. 04애니메이션

    캐릭터 애니메이션 제작 방식 전환

    상황
    원화를 만들 수 있어도 걷기에서 두 다리가 교차할 때 어느 부위가 앞뒤로 겹치고 드러나는지 자연스럽게 만들기 어려웠습니다. 같은 공정으로 계속 보정하면 남은 제작 시간에 필요한 동작을 확보하기 어려웠습니다.
    행동

    공격·이동 레퍼런스를 정리하고 ChatGPT로 만든 원화를 바탕으로 Claude를 활용해 몸통·팔·다리 분절과 리깅을 시도했습니다. 가려졌던 부분은 ComfyUI 인페인팅과 Photopea 후처리로 보완했습니다.

    보행의 다리 교차가 반복해서 어색해지는 것을 보고 기존 방식에 시간을 더 쓰는 대신 Blit.so와 Ludo.ai를 비교했습니다. 당시 비용과 제작 여건을 고려해 원화와 동작 프롬프트를 넣고 결과를 선별하는 Ludo.ai 방식으로 전환했습니다.

    결과
    필요한 캐릭터 애니메이션을 생산한 기록이 개인 경험문서에 남았습니다. 문서 리뷰에서는 결과의 형태와 팀에 전달한 과정을 이미지·기록으로 더 구체화하라는 피드백을 받았습니다.
    배울점
    도구 변경은 실패 지점과 비용을 기준으로 판단했습니다. 결과를 확보하는 능력과 내부 생성 공정까지 이해해 같은 제작 방식을 재현하는 능력은 따로 검토해야 합니다.
    제작 방식 비교

    계속 수정할 공정과 바꿀 공정을 판단한 기준

    공정시도판단
    초기 제작원화 → 부위 분절 → 리깅 → 빈 부분 보완보행 중 다리 교차와 가림을 안정적으로 처리하기 어려움
    대체 제작도구 비교 → 원화·프롬프트 입력 → 결과 선별필요 동작을 확보. 서비스 내부 생성 공정의 재현은 어려움

  5. 05VFX 제작

    총구 섬광·폭발탄·폭발의 기준 정리

    상황
    총구 섬광은 연사 중 시야를 가릴 수 있었고, 폭발탄 초안은 여러 무기에 공통으로 쓰기 어려운 전용 로켓처럼 보였습니다. 폭발도 채도와 발광이 강해 게임의 평면 카툰 색면과 어긋났습니다.
    행동

    섬광은 발사 방향과 고정 피벗을 유지하며 점화 후 빠르게 줄어드는 3프레임으로 정리했습니다. 폭발탄은 날개를 빼고 짧은 캡슐과 작은 추진부만 남겼습니다. 충돌 폭발은 투사체와 별도 자산으로 두고, 2~3단 색면·작은 흰 중심부·연한 연기·빠른 소멸을 각각 검토했습니다.

    구르기 먼지는 6개 후보 프레임 중 F1·F5·F6만 골라 0.5초 미리보기를 검토했습니다. 이후 외곽선을 절반 수준으로 낮추고 가운데 프레임의 크기를 약 85~90%로 줄이는 방향을 제시했습니다.

    결과
    폭발탄은 선택한 시트를 60×60 RGBA 8장으로 규격화했습니다. 원형 섬광은 3프레임, 얇은 외곽선 폭발은 261×301 RGBA 10프레임과 GIF 패키지로 정리했습니다. 먼지는 크기·선 수정 뒤 다시 묶은 개별 PNG까지 확인되지는 않았습니다.
    배울점
    리소스 피드백을 색·실루엣·크기·기준점·프레임 시간으로 나누면 무엇을 고칠지 분명해집니다. 제작용 파일을 넘길 때는 그림뿐 아니라 프레임마다 캔버스와 기준점이 같은지도 확인해야 합니다.

    행동

    결과

  1. 01데이터 정리

    성장 데이터의 편집 구조 단순화

    상황
    스탯 데이터가 여러 시트와 복잡한 수식에 흩어져 있어 기획자가 수치를 바꿨을 때 배수인지 합산인지 놓치기 쉬웠습니다.
    행동

    10개로 나뉜 안 대신 INFO·UpgradeTree·RebirthStat·ActiveSkill 중심으로 줄이고 이름의 한글·영어와 코드 키를 분리했습니다. 숫자 값과 연산 종류·수치 단위를 같은 뜻으로 혼용하지 않도록 요구했습니다.

    소수와 정수, 배수와 합산을 따로 표시하고 읽고 편집해야 하는 항목을 가까이 배치했습니다. 예를 들어 공격력 증가율과 최대 기력 증가는 수치뿐 아니라 적용 방식이 다릅니다.

    결과
    네 시트의 게임 데이터 수정본을 남겼습니다. 같은 성장 데이터에서도 수치, 증가량, 연산, 단위를 따로 읽을 수 있습니다.
    배울점
    편집 화면은 입력을 빠르게 하는 것과 입력값의 의미를 오해하지 않게 하는 것이 함께 중요합니다.

  2. 02밸런스 비교

    구매 정책별 성장 비교와 조정 후보 선정

    상황
    초반에는 자주 강화하고 중반에는 벽을 만나 환생하며 후반에는 다시 가속되는 감각을 목표로 삼았습니다. 같은 강화 비용도 가장 싼 것을 사는 사람과 생존·DPS를 우선하는 사람에게 다르게 작용할 수 있었습니다.
    행동

    Bills Must Be Paid·Clicker Heroes·AdVenture Capitalist의 성장 감각을 참고해 HTML Balance Lab에서 구매 전략과 비용·효과를 바꿔 비교했습니다. 진행 시간뿐 아니라 세션 길이와 반복 부담도 함께 봤습니다.

    조정 범위를 낙뢰의 초회 비용과 비용 배수로 좁혔습니다. 후보 선정에 쓰지 않은 시드 501~510을 기존안과 조정안, 두 구매 정책에 동일하게 적용했습니다.

    결과
    조정안에서 최저가 정책의 평균 진행 시간은 0.83분 짧아지고 생존·DPS 정책은 0.43분 길어졌습니다. 같은 수정이 구매 방식에 따라 반대 방향으로 작용하는 결과를 함께 기록했습니다.
    배울점
    한 정책의 평균만으로 전체 개선을 결론낼 수 없습니다. 후보를 고르는 데 쓴 실행과 비교 검증 실행을 분리하고, 모형에서 찾은 결과는 실제 플레이에서 다시 확인해야 합니다.

  3. 03보스 전투

    보스 패턴을 상태와 이벤트로 명세

    상황
    공격 쿨다운만 늘어놓으면 두 스킬이 같이 준비되거나 시전이 밀렸을 때 어느 공격이 나갈지 정할 수 없었습니다. 보스별 패턴과 실제 연출이 같은 동작을 설명하는지도 확인할 필요가 있었습니다.
    행동

    대기·공격·사망 상태, 스킬2 → 스킬1 → 기본 공격의 우선순위, 지연된 쿨다운과 실제 발사 시점을 구분했습니다. 30초 종료 시점에 보스가 죽었다면 사망 판정을 우선하도록 검토했습니다.

    보스 공격은 예상 플레이어 체력÷15, 보스 체력은 목표 DPS×15초를 기준으로 안을 제안했습니다. 로켓 주먹의 돌아오는 공격이 새 이미지의 늘어나는 팔로 보이는 차이를 짚었고, 슈퍼로봇 레이저는 발사부·확장·접합·총구를 나누어 수정했습니다.

    결과
    공통 전투 규칙과 보스별 명세를 정리했습니다. 보스 1~6과 우주 테마 7·8의 초안 수준을 구분했고, 레이저는 여러 작업 버전 이후에도 총구 기준으로 처음부터 다시 제작하는 요청이 남았습니다.
    배울점
    패턴이 재미있어 보이는 것과 구현·연출이 같은 규칙으로 동작하는 것은 별개입니다. 우선순위, 판정 시점, 실제 움직임을 한 명세에서 대조해야 합니다.
    보스 명세 수치

    공격 우선순위와 수치 가정

    항목명세 기준해석
    공격 중첩스킬2 > 스킬1 > 기본 공격여러 공격이 준비됐을 때 선택 기준
    목표 피해보스 공격 ≈ 예상 플레이어 체력 ÷ 15약 15회 피격을 기준으로 잡은 설계 가정
    목표 체력보스 체력 = 목표 DPS × 15초처치 목표 시간 12~20초, 전투 제한 30초

  4. 04그래픽 검수

    스킬 VFX와 자원 그래픽의 제작 조건

    상황
    브레스·낙뢰·메테오·지진을 구분할 수 있어야 했고, 자원은 드랍·도감·정산 화면의 서로 다른 크기에서도 같은 아이콘으로 읽혀야 했습니다.
    행동

    팀의 비주얼 가이드를 기준으로 생성·후처리를 지시하고 이펙트별 모양과 타이밍을 비교했습니다. 540×540, 12프레임·24fps 같은 제작 기준을 정리하고 프레임마다 피벗과 중심이 흔들리지 않도록 했습니다.

    자원 아이콘은 외곽선을 더 굵게 요청하고 1,254px로 잘못 커진 결과를 540×540으로 수정하도록 했습니다. 드랍에서 작은 크기로 보이는 경우를 32·48·96px 미리보기로 확인했습니다.

    결과
    스킬과 자원 그래픽 후보, 수정본, 크기별 검토 이미지를 정리했습니다. 인계 기록에서 확정·미확정·리젝 자산을 구분했습니다.
    배울점
    공통 그림체를 맞추는 일은 스타일 지시뿐 아니라 게임에서 쓰이는 크기, 외곽선, 프레임, 기준점을 함께 검수하는 일입니다.

  5. 05사운드 검수

    효과음 후보 비교와 편집 피드백

    상황
    같은 스킬이라도 준비·첫 타격·지속·잔향이 서로 다른 역할을 합니다. 원본 음원이 비슷해 보인다는 이유만으로 선택하면 스킬의 타이밍이나 무게를 전달하기 어렵습니다.
    행동

    49개 선택 항목을 23개 용도와 37개 리소스로 연결하고 이미 확정된 7개를 유지했습니다. 지진은 준비·첫 충격·반복 한 박을 구분하고 낙뢰는 첫 충격과 짧은 전기 잔결을 따로 들었습니다.

    미채택 하위 효과 31개에 후보 6개씩을 두어 186개 비교 항목, 중복 제외 147개 원본을 듣고 비교할 수 있게 했습니다. 현대 공격음의 거친 성분을 줄이는 EQ 의견과 일반 루프·보스 인트로→루프 등 편집 방향도 정리했습니다.

    결과
    용도별 후보와 청취 비교 도구, 편집 피드백을 남겼습니다. 제공 보고서에 WAV 19개 편집이 기록돼 있으나 원본 파일과 최종 적용은 이 자료에서 확인되지 않았습니다.
    배울점
    청취 피드백은 좋고 나쁨보다 어느 순간의 공격감·재질·길이·잔향을 살릴지로 써야 교체나 편집 기준이 됩니다.

  6. 06OBT 검수 설계

    OBT 핵심 테스트 명세 정리

    상황
    CBT와 OBT의 Windows 빌드를 비교할 때 기존 23개 항목을 그대로 가져가면 새 기능과 핵심 흐름이 빠지고, 세부 경계까지 모두 넣으면 우선순위를 보기 어려웠습니다.
    행동

    CBT 0.5.0과 OBT 0.6.2에서 달라진 기능을 확인하고 자동 전투·알과 부화·유물·스킨·도감·저장 등 본편 중심으로 재구성했습니다. 기존 저장·불러오기 항목은 새 게임의 취소·확정에 따른 초기화 검증으로 바꿨습니다.

    디버그로 건너뛴 진행과 자연 성장 검증을 분리했습니다. 언어가 한국어에서 영어로 돌아가는 현상은 CBT에도 있는지 비교해 기존 문제와 새 회귀를 구분하려 했습니다.

    결과
    기능별 확인 방법과 기대 결과가 있는 핵심 35개 케이스를 남겼습니다. 수정본의 상태는 모두 대기이며 확인 메모는 비어 있습니다.
    배울점
    테스트 케이스의 작성과 실행 결과는 다릅니다. 기대 결과를 명확히 적고 버전과 진행 조건을 남겨야 재현과 회귀 판단이 가능합니다.

    OBT에서 확인할 기능과 기대 동작

자료에서 확인

추가할 증거
